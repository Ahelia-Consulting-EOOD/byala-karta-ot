## 3. Алгоритъм за съчетаване на спирки и населени места

### 3.1 Стратегия

Двустепенен подход:

1. **Стъпка 1 - Административно текстово съчетаване** (93,6%)
2. **Стъпка 2 - Пространствена близост (Spatial Fallback)** (6,2%)

### 3.2 Стъпка 1: Административно текстово съчетаване

Всяка БДП спирка има полета `oblast`, `municipal`, `city_vila`. Алгоритъмът нормализира стойността на `city_vila` преди съчетаването:

**Правила за нормализация:**

| Правило | Пример | Резултат |
|---------|--------|----------|
| Премахване на районни квалификатори | `"София-град - район Витоша"` | `"София-град"` |
| Премахване на квартални квалификатори | `"Бургас, кв. Сарафово"` | `"Бургас"` |
| Премахване на префикси за тип | `"с. Самораново"` | `"Самораново"` |
| Премахване на пощенски кодове | `"[6280] гр. ГЪЛЪБОВО"` | `"ГЪЛЪБОВО"` |
| Специални съпоставки | `"София-град"` | `"София"` |
| Специални съпоставки | `"Велико Търнов"` | `"Велико Търново"` |

**Приоритет на съчетаване:**

1. **name_muni** - точно съвпадение на нормализираното име + общината
2. **name_oblast** - при множество ЕКАТТЕ кандидати, филтър по област
3. **name_only** - ако има единствен кандидат с това име

**Резултати от текстовото съчетаване:**

| Метод | Спирки | % |
|-------|--------|---|
| name_muni | 9 528 | 92,7% |
| name_only | 48 | 0,5% |
| name_oblast | 46 | 0,4% |
| Без съвпадение | 276 | 2,7% |
| Без стойност за city_vila | 382 | 3,7% |
| **Общо съчетани** | **9 622** | **93,6%** |

### 3.3 Стъпка 2: Пространствена близост

За 658-те несъчетани спирки: намиране на най-близкото населено място в радиус от 5 km чрез формулата на Haversine.

**Резултат:** 633 от 658 допълнително съчетани.

| Случай | Описание | Решение |

## 8. Валидация и качество на данните

### 8.1 Правила за валидация по полета

| Поле | Правило | Описание |
|------|---------|----------|
| `ekatte` | `^[0-9]{5}$` | Точно 5 цифри |
| `name` | не е празен | Кирилица, поне 1 символ |
| `name_en` | не е празен | Латиница, поне 1 символ |
| `type` | `IN ("с.", "гр.", "ман.")` | Само допустими стойности |
| `oblast_code` | `^[A-Z]{3}$` | Точно 3 главни латински букви |
| `nuts1` | `^BG[34]$` | BG3 или BG4 |
| `nuts2` | `^BG(3[1-4]|4[1-2])$` | Един от 6-те NUTS2 кода |
| `nuts3` | `^BG(31[1-5]|32[1-5]|33[1-4]|34[1-4]|41[1-5]|42[1-5])$` | Един от 28-те NUTS3 кода |
| `population_permanent` | `>= 0 OR NULL` | Неотрицателно цяло число или null |
| `population_current` | `>= 0 OR NULL` | Неотрицателно цяло число или null |
| `lon` | `22.35 <= lon <= 28.61 OR NULL` | В границите на България |
| `lat` | `41.23 <= lat <= 44.21 OR NULL` | В границите на България |
| `has_pt_access` | `boolean` | true/false |
| `bdp_stop_count` | `>= 0` | Неотрицателно цяло число |
| `bdp_stop_count` и `has_pt_access` | Консистентност | `has_pt_access == (bdp_stop_count > 0)` |

### 8.2 Известни проблеми с качеството на данните

### 8.3 Процедура за обновяване на данните

**Периодичност:** Препоръчва се обновяване на тримесечие.

**Стъпки:**

1. **ЕКАТТЕ:** Изтегляне на актуален архив от https://www.nsi.bg/nrnm/ekatte/index. Проверка за нови/заличени населени места.

2. **ГРАО население:** Изтегляне на актуален файл от https://www.grao.bg/tables.html. Конвертиране от Windows-1251 в UTF-8. Парсване и съчетаване с ЕКАТТЕ.

3. **Координати:** При наличие на нови н.м. без координати - допълване от yurukov/Bulgaria-geocoding или ръчно геокодиране.

4. **БДП спирки:** Извличане чрез GIS Cloud REST API (`GET /1/layers/6542284/features.json`). Конвертиране от EPSG:3857 в WGS84. Изпълнение на двустепенния алгоритъм за съчетаване.

5. **Обединяване:** Стартиране на скрипта за обединяване. Валидация по правилата от раздел 8.1. Генериране на нов `bg_settlements_with_pt.json`.

6. **Верификация:** Сравнение на агрегираните статистики с предишната версия. Маркиране на значими промени (> 5% промяна в покритието за дадена област).

7. **Публикуване:** Обновяване на GeoJSON endpoints. Актуализиране на метаданните за дата на последно обновяване.

**Забележка:** Границите на ниво ADM3+ (населено място) НЕ са налични в geoBoundaries за България. При бъдеща необходимост могат да бъдат извлечени от OpenStreetMap чрез Overpass API, но покритието е непълно и не е гарантирано за всички 5 256 населени места.

**Описание:** Полигонални граници на 28-те области на България.

```json
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "geometry": {
        "type": "Polygon | MultiPolygon",
        "coordinates": [[[...]]]
      },
      "properties": {
        "shapeName": "Plovdiv",
        "shapeISO": "BG-16",
        "shapeID": "BG-ADM1-3_0_0-B1",
        "shapeGroup": "BGR",
        "shapeType": "ADM1"
      }
    }
  ]
}
```

**Полета в `properties`:**

| Поле | Тип | Описание | Пример |
|------|-----|----------|--------|
| `shapeName` | string | Име на областта на латиница | `"Plovdiv"` |
| `shapeISO` | string | ISO 3166-2 код на областта | `"BG-16"` |
| `shapeID` | string | Уникален идентификатор в geoBoundaries | `"BG-ADM1-3_0_0-B1"` |
| `shapeGroup` | string | ISO 3166-1 alpha-3 код на държавата | `"BGR"` |
| `shapeType` | string | Административно ниво | `"ADM1"` |

**Тип геометрия:** Повечето области са `Polygon`, но някои с островни или несвързани територии са `MultiPolygon`.

### 9.4 Стратегия за съчетаване на имената

Данните от geoBoundaries съдържат имена на латиница (`shapeName`), докато основният набор данни използва кирилица. Необходимо е съчетаване (matching) за свързване на полигоните с вътрешните данни.

**Подход:**

1. **Изграждане на lookup таблица:** латинско `shapeName` -> българско име на областта/общината
2. **Кръстосана проверка:** Използване на полето `name_en` от данните за населените места (ЕКАТТЕ) за верификация
3. **Съчетаването е case-insensitive** (без значение на главни/малки букви)

**Специални случаи при ADM1:**

| shapeName (geoBoundaries) | Област (кирилица) | Забележка |
|---------------------------|-------------------|-----------|

| `"Sofia"` | София | Софийска област, NUTS3 = BG412, oblast_code = SFO |
| `"Veliko Turnovo"` | Велико Търново | Различно транслитериране |
| `"Kurdjali"` | Кърджали | Различно транслитериране |

### 9.5 Ограничения и бъдещо разширяване

**Налични данни:**
- ADM1 (области) и ADM2 (общини) са с пълно покритие от geoBoundaries
- Качеството на полигоните е подходящо за визуализация в мащаб 1:250 000 и по-малък

**Ненаправени данни:**
- Граници на ниво населено място (ADM3+) НЕ са налични от geoBoundaries за България
- При бъдеща необходимост от граници на населени места, възможни подходи са:
  1. **OSM Overpass API** - извличане на `boundary=administrative` + `admin_level=8` релации. Покритието е непълно и неравномерно
  2. **Voronoi/Thiessen полигони** - генериране на приблизителни граници от точковите координати на населените места. Не отразяват реалните административни граници
  3. **Кадастрална карта (КАИС)** - точни граници, но с ограничен достъп и лицензионни условия
